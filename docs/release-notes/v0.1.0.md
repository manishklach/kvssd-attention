# KVSSD Attention v0.1.0

The first public release delivers an end-to-end reference implementation for keeping 2-bit or 4-bit
KV-cache blocks on SSD, asynchronously staging selected blocks, and consuming the packed representation
inside a fused CUDA decode-attention kernel.

## Highlights

### Storage designed for the data path

KV blocks are stored in fixed-size, 4 KiB-aligned records rather than generic tensor archives. Each
record identifies its layer and block, carries the complete quantization layout, distinguishes valid
tokens from final-block padding, and protects its payload with CRC32. The manifest provides stable
offset lookup without scanning the data file.

### INT2/INT4 values stay packed until use

Keys and values use symmetric groupwise quantization with FP16 scales. The fused CUDA kernel extracts
each packed code and applies its scale in registers while calculating query-key scores and weighted
values. It does not allocate or write a full FP16 KV cache in GPU memory.

### Bounded asynchronous pipeline

Selected records are prefetched through a bounded worker pool, detached safely from reusable I/O slots,
coalesced in pinned host buffers, and copied asynchronously to the GPU. Dedicated transfer and compute
streams permit the next chunk's SSD/H2D work to overlap the current chunk's attention kernel.

### Exact attention across chunks

Each staged chunk returns its normalized result and log-sum-exp statistic. Chunk results are merged with
the exact softmax identity, so bounded staging does not introduce a second approximation beyond KV
quantization itself.

### Reference path and fail-closed deployment

The CPU implementation provides inspectable numerical semantics and portable tests. Deployments can set
`require_cuda_kernel=True` or pass `--require-cuda`, preventing an accidental performance benchmark of
the reference fallback.

## Supported CUDA contract

- One query token per decode call.
- INT2 or INT4 packed KV cache with FP16 scales.
- FP16, BF16, or FP32 queries.
- MHA, MQA, and GQA head mappings.
- Head dimension up to 256 and divisible by the configured group size.
- Partial final blocks masked through `valid_tokens`.

## Quality and verification

The release passes 12 portable tests covering quantization error bounds, packing size, partial-block
padding, CRC corruption, asynchronous buffer ownership, concurrent descriptor opening and cleanup,
GQA validation, packed/reference equivalence, exact chunk merging, selectors, and the CPU end-to-end
pipeline. Ruff and Python package builds also pass.

The development system has an AMD GPU. WSL exposes a CUDA compiler but no NVIDIA CUDA device or driver.
Consequently, this release intentionally makes no physical-GPU correctness or performance claim. The
next validation milestone is comparison against the reference implementation plus Compute Sanitizer and
Nsight Systems runs on an NVIDIA A10, L4, A100, H100, or newer compatible GPU.

## Installation

Portable reference path:

```bash
pip install -e '.[dev]'
pytest
```

CUDA extension path:

```bash
pip install torch --index-url https://download.pytorch.org/whl/cu128
KVSSD_BUILD_CUDA=1 pip install -e . --no-build-isolation
kvssd benchmark --tokens 131072 --bits 4 --require-cuda
```

Select the PyTorch CUDA build appropriate for the target driver instead of treating `cu128` as a fixed
requirement.

## Known limitations

- This is a reference runtime component, not a complete vLLM or TensorRT-LLM integration.
- The CUDA kernel prioritizes readable correctness over architecture-specific tensor-core optimization.
- Included selection policies are structural; semantic retrieval and block-centroid indexing are future
  integration points.
- The default SSD backend uses buffered reads. Direct I/O and GPUDirect Storage are not implemented.
- INT2 quality is model- and workload-dependent and must be evaluated before deployment.
- Production CUDA execution targets Linux with NVIDIA hardware.

## Upgrade notes

This is the first public format version, so there are no migrations. Future incompatible record changes
will increment the on-disk format version and require explicit reader compatibility tests.
