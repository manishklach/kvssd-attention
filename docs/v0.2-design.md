# v0.2 expansion design

## Objective

Version 0.2 turns the original CUDA vertical slice into a small backend-oriented system that can be
adopted and evaluated from an existing serving runtime. It adds three capabilities without weakening
the v0.1 invariants:

1. a Triton fused decode-attention backend for NVIDIA and AMD/ROCm;
2. a GPUDirect Storage backend that reads aligned packed records into device memory and fails over to
   the pinned-host path when direct I/O is unavailable;
3. a vLLM integration built against the public V1 KV connector/offloading interfaces.

The project will not claim physical-GPU support for a backend until that backend passes numerical and
lifecycle tests on the corresponding hardware.

## External compatibility targets

| Component | Minimum target | Contract used |
|---|---:|---|
| Python | 3.10 | Core package and reference tests |
| PyTorch | 2.4 | Tensor ownership, streams, extension ABI |
| Triton | 3.2 | JIT kernel API; optional dependency |
| NVIDIA CUDA | 12.2 | cuFile stream API baseline |
| AMD ROCm | 6.2 | Triton AMD backend baseline |
| vLLM | 0.25 | V1 KV connector/offloading interfaces |

These are integration targets rather than unconditional core dependencies. Importing `kvssd` on a
CPU-only machine must remain supported.

## Backend architecture

```text
KVSSDPipeline
  ├── BlockSelector
  ├── StorageBackend
  │     ├── BufferedBackend       preadv → CPU tensor
  │     ├── DirectIOBackend       O_DIRECT → aligned pinned tensor
  │     └── CuFileBackend         bounded worker cuFileRead → packed GPU tensor
  └── AttentionBackend
        ├── ReferenceBackend      unpack/dequantize with PyTorch
        ├── CudaExtensionBackend  hand-written CUDA kernel
        └── TritonBackend         NVIDIA CUDA or AMD ROCm
```

Selection, storage movement, and attention execution are independent decisions. A Triton attention
backend may consume data delivered through buffered storage, and a cuFile storage backend may feed the
CUDA extension. No backend is allowed to silently replace a requested backend: automatic selection is
observable, while explicit selection fails closed.

## Common attention contract

An attention backend consumes:

- query `[query_heads, head_dim]`;
- packed keys and values `[blocks, block_tokens, kv_heads, packed_dim]`;
- FP16 scales `[blocks, block_tokens, kv_heads, groups]`;
- valid-token counts `[blocks]`;
- bit width, group size, and softmax scale.

It returns normalized output `[query_heads, head_dim]` plus log-sum-exp `[query_heads]`. Returning the
normalizer is mandatory because the pipeline merges independently staged chunks exactly.

Backend capability metadata includes supported devices, bit widths, query dtypes, head dimensions,
and whether physical hardware validation has been recorded.

## Triton backend

The first Triton kernel preserves the v0.1 algorithm rather than introducing a second quantizer:

- INT2 and INT4 low-bit-first unpacking;
- FP16 group scales;
- GQA head mapping;
- masked final blocks;
- FP32 score accumulation and online softmax;
- FP32 chunk output and log-sum-exp.

`TRITON_INTERPRET=1` provides CPU-based functional debugging for the subset of operations supported by
the interpreter. Hardware test markers separate CUDA and ROCm jobs. The backend is optional and lazily
imported so Windows and CPU packaging remain intact.

## Storage interface and GDS behavior

Every storage backend reports a structured availability result containing `available`, `direct`, and a
human-readable reason. Automatic selection follows:

```text
cuFile direct path
  → O_DIRECT pinned-host path
  → buffered preadv path
```

The cuFile backend requires Linux, `libcufile`, a CUDA device, a supported filesystem/file descriptor,
and compatible record/buffer alignment. Initialization probes these conditions before serving reads.
Runtime cuFile failures are surfaced with the layer, block, offset, byte count, and cuFile error; fallback
after initialization is opt-in because silently changing the data path invalidates benchmarks.

The first implementation uses a small C++/CUDA binding rather than `ctypes`, ensuring CUDA stream and
device-pointer lifetimes are controlled by PyTorch tensors. Builds without cuFile headers simply omit
the backend.

## vLLM integration

The proof of concept targets vLLM's V1 offloading/connector surface rather than patching PagedAttention.
It provides:

- a custom offloading spec importable by module path;
- mapping between vLLM cache groups/blocks and KVSSD record identifiers;
- asynchronous store/load lifecycle hooks;
- explicit configuration validation for block size, dtype, parallel rank, and model identity;
- an example `vllm serve` invocation and a prefix-reuse benchmark.

The initial adapter uses vLLM's CPU primary tier for compatibility. When both runtimes expose a stable
direct-secondary-tier contract, the same adapter can opt into cuFile without changing the stored record
format.

## Acceptance criteria

### Portable kernel

- Matches dequantized reference output for INT2/INT4, MHA/MQA/GQA, partial blocks, and at least three
  head dimensions.
- Chunked results match a single full-cache invocation.
- Explicit Triton selection fails clearly when Triton or a supported GPU is unavailable.
- CUDA and ROCm benchmark output includes backend, device, software versions, and tensor shape.
- Hardware jobs preserve raw numerical results and runner/GPU metadata as downloadable artifacts.

### GDS backend

- Capability probing is unit-tested without requiring NVIDIA hardware.
- All offsets and buffer sizes are checked before submission.
- Short reads and cuFile errors preserve block-level diagnostics.
- Fallback choice is visible in CLI and benchmark JSON.
- A hardware test verifies bytes read directly into a CUDA tensor and CRC equality.
- GDS tests and benchmarks execute under an explicitly named qualified NVMe mount, never an implicit
  temporary directory.

### vLLM integration

- Import and configuration tests run against the supported vLLM version.
- A fake-runtime contract test covers scheduling and block mapping without a GPU.
- A GPU integration test demonstrates store, eviction, reload, and prefix reuse.
- Documentation distinguishes native vLLM filesystem offloading from KVSSD packed/direct behavior.

### Release

- v0.1 tests remain green.
- Optional-dependency and platform CI matrices pass.
- No throughput claim is published without raw reproducible benchmark output.
- Release notes enumerate hardware-validated and compile-only paths separately.
- The release retains JUnit, benchmark JSONL, tested commit, GPU, storage, mount, and topology evidence
  from both physical hardware jobs.

## Out of scope for v0.2

- Prefill, speculative decoding, continuous batching, and semantic top-k kernels.
- NVMe-oF, RDMA, and multi-node cache coherence.
- TensorRT-LLM, SGLang, llama.cpp, or Hugging Face integrations.
- A new quantization format such as FP8, NF4, or asymmetric INT2.

Those remain valuable follow-on work once the three backend contracts above have been validated.
